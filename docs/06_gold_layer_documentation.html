Gold Layer Documentation

A local Dockerized Medallion (Bronze/Silver/Gold) MySQL data warehouse covering population demographics, disease surveillance, and economic/local-area data for a hospital catchment area in Bangkok. This page documents the Gold layer: the Star Schema foundation plus the derived OBT, aggregate, and feature-store tables built on top of it.

Architecture

Bronzeraw ingestion, 1:1 with source files, typed as text/varchar
→
Silverconformed, typed, deduplicated — still source-shaped
→
Gold — Star Schemadim_/fact_, cross-source geography & taxonomy resolved
→
Gold — Derivedobt_ / agg_ for BI, feat_ for ML — always derived from the star, never from Silver directly
The Gold layer serves two consumers with different physical requirements. Metabase dashboards need sub-second reads, so every dashboard query hits a denormalized obt_ (One Big Table) or a pre-aggregated agg_ table — never a runtime join across the star schema. ML pipelines (cold-start geographic segmentation, Bayesian spatial-temporal models) need a flat, wide feature vector, so feat_ tables are built at the natural modeling grain — geography×time for the spatial-temporal model, and one entity-level example (feat_factory) for clustering/segmentation. Both consumer layers are derived from the star schema, never loaded from Silver directly, so every data-quality fix (deduplication, name normalization, rollup-row exclusion) lives in exactly one place.

Conventions

RuleDetail
Namingdim_, fact_, obt_, agg_, feat_ prefixes, snake_case throughout.
Surrogate keysINT UNSIGNED AUTO_INCREMENT PRIMARY KEY on every dimension. Exception: dim_date uses the Kimball convention of a meaningful integer key (YYYYMMDD, e.g. 20240101) so date-range filters don't need a join.
SizingNo blanket VARCHAR(255). Every column width is sized from an observed real maximum plus margin (e.g. Thai admin names cap at 108 observed chars → VARCHAR(150); disease/report names cap at 260 observed → VARCHAR(300)).
IndexingEvery FK indexed. Every fact table carries a composite (geo_key, date_key) index — the universal join pattern into OBT/agg. Facility-grain facts (e.g. HDC's hospital/area data) additionally index the facility-level natural key, since a geography-level index alone can't support a facility-grain self-join without a full scan.
Full refreshEvery script is DROP TABLE IF EXISTS + rebuild — no incremental logic, consistent with Bronze/Silver. SET FOREIGN_KEY_CHECKS = 0/1 wraps any table that's referenced by a FK from a table built later in the run, so reruns don't fail on stale constraints.
Cross-source joins happen onceGeography name normalization, disease-code decoding, and sex/age normalization all happen in the dimension build, not re-derived in every fact/OBT/agg query.

Stage 1 — Population & Demographics DOPA · NSO · other_health

dim_date dim13,879 rows

Grain: one row per calendar day, 1993-01-01 to 2030-12-31.
ColumnTypeNotes
date_keyINT PKYYYYMMDD, e.g. 20240101
full_dateDATE
year_ce / year_beSMALLINTGregorian and Thai Buddhist Era years
quarter / month / dayTINYINT
month_nameVARCHAR(20)"January".."December"
is_month_startTINYINT(1)
Gotcha: populated via a non-recursive cross-join-of-digit-tables generator, not a recursive CTE — MySQL 8.0's default cte_max_recursion_depth (1000) would silently truncate the ~13,900-day series. DATE_FORMAT(d,'%B') also returned the literal string "B" instead of a month name on this server despite correct locale settings — worked around with an explicit ELT() lookup instead of relying on server locale at all.

dim_geography dim13,018 rows

Grain: one row per administrative unit (country / province / district / subdistrict), self-referencing hierarchy via parent_geo_key.
ColumnTypeNotes
geo_keyINT UNSIGNED PK
admin_levelVARCHAR(12)country | province | district | subdistrict
province_code / district_code / subdistrict_codeVARCHAR(10/15/15)DOPA government codes — the reliable cross-source join key
province_name_th / district_name_th / subdistrict_name_thVARCHAR(150)Canonical name, one per code
parent_geo_keyINT UNSIGNED NULLSelf-FK; NULL for 10 subdistricts with no matching district row (real gap, not a bug)
source_systemVARCHAR(50)
Bug found & fixed: dedupes by administrative code alone, picking the latest name per code (via GROUP_CONCAT + SUBSTRING_INDEX ordered by yymm DESC). The original approach deduped by (code, name) together — several codes were reclassified over DOPA's 30-year span (e.g. a district renamed from เทศบาลเมือง to เทศบาลนคร, same code), which produced 2+ dimension rows per code and silently doubled every fact-table join on that code.

dim_age_sex dim317 rows

Grain: one row per distinct (sex, age_exact, age_qualifier) combination actually observed.
ColumnTypeNotes
age_sex_keyINT UNSIGNED PK
sexVARCHAR(10)male | female | total
age_exactSMALLINT NULLNULL for bucket/total qualifiers or when age doesn't apply
age_qualifierVARCHAR(10) NULLexact | le | ge | gt | lt | total | other; NULL when there's no age dimension at all
Gotcha: 3 extra rows — (male,NULL,NULL), (female,NULL,NULL), (total,NULL,NULL) — represent "sex applies, age doesn't" for other_health's 5 non-age-bracket components (grand_total, non_thai_national, etc). Without these, an inner join from the fact table would silently drop every row for those components.

dim_population_component dim12 rows

Grain: one row per (source_system, component_code) — NSO's 6 DEM_IND* indicator codes + other_health's 6 component_type strings.
Design note: is_headline_total deliberately isn't a column here — it depends on the (component, sex) combination, not the component alone (other_health's grand_total pairs with sex=male/female too, but only sex=total is the real headline figure). It lives on the fact table instead.

fact_population_by_area fact349,983 rows

Grain: geo_key × date_key × admin_level. Sources: DOPA's monthly area file + population_by_tambon_national, is_rollup_row=0 applied at load.
ColumnTypeNotes
male_count / female_count / total_count / house_countBIGINT
source_systemVARCHAR(20)dopa | other_health
Reconciled exactly against filtered Silver counts: province/dopa 2,138; district/dopa 56,646; subdistrict/dopa 282,353; subdistrict/other_health 8,846. Spot-checked against known real figures (Bangkok Dec-2024: 5,455,020; national Dec-2020: 66,186,727).
Known overlap: Dec-2025 subdistrict data appears from both DOPA's own snapshot and other_health's population_by_tambon_national — same underlying government data, two delivery paths, kept as separate rows per this project's no-cross-source-merge rule.

fact_population_age_sex fact82,105 rows

Grain: geo_key × date_key × age_sex_key × component_key. NSO's national rows map to the 'country' geo_key.
Gotcha, confirmed by direct testing: is_headline_total=1 alone is not safe to SUM() — it only narrows to the DEM_IND24 indicator, which has one row per (sex × age) slice. Summing without also filtering sex='total' AND age_qualifier='total' returns 2–4× the real figure (confirmed: country-level 2024 read 263,804,840 — 4× the real 65,951,210 — until both filters were added).

obt_population_by_geography obt349,983 rows

Grain: one row per (geography, month) — fully denormalized for Metabase, zero joins at query time.
Growth rates (pop_growth_mom_pct, pop_growth_yoy_pct) are computed via an explicit self-join on the exact prior calendar period, not a sequential LAG() window function — this source's real cadence is mostly one December snapshot per year, so LAG()'s "previous row in the partition" would silently compare across a multi-year gap and mislabel it "MoM". The self-join correctly returns NULL when no exact prior period exists.

agg_population_summary_yearly agg341,149 rows

Grain: geo_key × year. Pre-computes yoy_growth_pct, age_dependency_ratio, aging_index, non_thai_national_pct.
Coverage gap, by design: fact_population_by_area never has a country-level row, and DOPA's province series stops at Dec-2020 while NSO's province age-breakdown is 2024-only. A second NSO-sourced insert seeds country/province rows for years DOPA doesn't cover, using DEM_IND24 (sex=total, age=total) as the base total.
Within NSO: the age-independent grand total spans 2017–2025, but the detailed single-year-of-age breakdown needed for age_dependency_ratio/aging_index exists only for 2024 — so non_thai_national_pct populates for all 9 years while the two age-band ratios populate for 2024 only (confirmed plausible: 41.65% dependency ratio, aging index 94.19, consistent with Thailand's known aging trend).

feat_geography_month feat349,995 rows (+ 5 disease columns from Stage 2)

Grain: geo_key × date_key (month) — the geography×time feature store for the spatial-temporal ML model.
ColumnNotes
pop_density_proxyLiterally = total_count — no land-area source exists in this warehouse yet. Documented stand-in, not a real density.
pct_age_0_14 / pct_age_15_64 / pct_age_65_plusSame NSO/other_health gap as the agg table, at monthly grain.

Stage 2 — Disease Surveillance DDS · HDC · other_health · NCD/cause-of-death sources

dim_disease dim220 rows

Grain: one row per (source_system, disease_code) — scoped per source, not a unified taxonomy.
Design decision: 7 sources' disease vocabularies are disjoint and don't line up 1:1 — DDS has 85 Thai disease names, sick_298group uses numbered labels ("104 เบาหวาน"), HDC uses short English codes (dm, ht, ihd...), cause_of_death uses its own phrasing. No reliable automated crosswalk exists between them, so cross-source disease rollups are explicitly out of scope — fabricating one would be worse than not having it.

fact_disease_event fact3,223 rows

Grain: geo_key (nullable) × date_key × disease_key × age_sex_key (nullable). Covers 7 count/death-based sources via generic measure slots (case_count, death_count, rate_per_100k, plus DDS-only ipd_count/case_fatality_rate_pct).

Duplicate source avoided: cause_of_death_top10_no_rate and _with_rate are confirmed identical data (same province/years/counts) — only the with-rate variant is loaded.

fact_disease_incidence_hdc fact507,628 rows

Grain: geo_key (district, nullable) × date_key × disease_key × grain (monthly|annual). HDC's target/result KPI tracking — genuinely different measure shape from count/death facts.
Unpivoted from hdc_incidence_monthly's fiscal-year columns (result10/11/12 = Oct–Dec of year-1, result01..09 = Jan–Sep of the labeled year, per the Thai government fiscal year convention) into 12 calendar-month rows per source row.
ihd is annual-only: hdc_incidence_annual tracks disease='ihd' exclusively; the monthly table never has it. target_alt/result_alt hold a second target/result pair present in the annual source with no surviving documentation of how it differs from the primary pair.
geo_key resolves via areacode's first 4 digits against dim_geography.district_code (confirmed 100% match, 1,669/1,669 distinct codes) — 21 source rows (252 of 498,936 monthly rows, 0.05%) have province_code disagreeing with the areacode's own embedded province prefix, a genuine source inconsistency; geo_key stays NULL for those rather than guessing.
Performance bug found & fixed: the real fact grain is per-facility (hospcode+areacode), not per-district. A derived table's self-join initially matched on district-level geo_key alone, which fanned every hospital in a district against every other — 42.5M rows from 507K facts. Fixed by joining on the facility key instead, plus adding the missing composite index — without it, the corrected join was still a full table scan taking 85+ minutes.

obt_disease_surveillance obt510,851 rows

UNION ALL of both disease fact tables (not a join) — they're genuinely different grains, so each side populates what it has and leaves the rest NULL, distinguished by a grain column.

agg_disease_kpi_monthly agg507,817 rows

Two natural grains, same UNION-not-join approach: case_fatality_rate_pct (DDS, year-grain, YoY matched on health_region_code since DDS has no geo_key) and target_attainment_pct (HDC, monthly+annual, YoY matched on facility key).
YoY for target_attainment_pct is a percentage-point difference (this period's attainment % minus last period's), not a relative percent change — avoids distorted math when comparing two already-percentage values.

feat_geography_month extension (Stage 2)

5 new nullable columns added via ALTER TABLE: incidence_rate_dm, _ht, _copd, _coronary (monthly), _ihd (annual-only, so only populates January rows). Scoped to exactly the 5 diseases actually present in fact_disease_incidence_hdc — not all 11 HDC diseases exist at this grain (stroke/asthma/the 3 cancers/emphysema are tracked elsewhere, in tables not loaded into this fact).

Stage 3 — Economic & Local-Area factory_list · KMCH catchment sources

dim_factory dim5,976 rows

Grain: one row per distinct factory_reg_no — collapsed from 11,862 registration records using the latest record per factory (same latest-wins convention as dim_geography).

dim_place dim1,672 rows

Generic place dimension covering 8 KMCH-catchment sources: kmch_catchment_places (1,333), business_establishment (264), religious_site (23), safety_risk_point (14), edu_school (20), edu_university (2), edu_vocational_college (14), health_hospital (2).
Out of scope by design: community_count_by_district_bkk, foreign_labor_permit_by_area_bkk, and labor_force_survey are district/area-level aggregates, not individual places — they don't fit this place-grained dimension and remain available in Silver for a future extension.

fact_factory_registration fact11,862 rows

Grain: one row per factory_list record — a real event log (multiple registration records per factory over time), not one-row-per-factory. date_key = permit_year_ce.
Join fan-out bug found & fixed: geography resolves via a compound (district, sub_district) text match, since subdistrict names alone are ambiguous within Bangkok (e.g. "อนุสาวรีย์" matches more than one candidate before district disambiguation narrows it). Resolving this with a two-step inline LEFT JOIN still fanned out before disambiguation could apply, producing 815 duplicate rows (12,677 instead of 11,862). Fixed by pre-resolving each distinct (district, sub_district) pair to a single geo_key in a deduplicated lookup before joining to the fact query.

fact_catchment_place fact1,672 rows

One row per dim_place row. Generic measure slots shared across the 8 sources (investment_thb, avg_distance_km, student_count, risk_flag_1..6, etc.) — each source populates what it has.
geo_key only resolves for 1 of the 8 sources (kmch_catchment_places, via the same compound match as factory registration). The other 7 have either a free-text address only, or — confirmed by inspection — no geography column survived their Bronze→Silver transform at all (safety_risk_point's bronze table has a district column; Silver's doesn't).
risk_flag_1..risk_flag_6 (safety_risk_point's r1–r6) are confirmed binary flags with no surviving documentation of what each specifically represents — kept opaque rather than guessing labels.

obt_economic_by_geography obt13,534 rows

UNION ALL of both economic fact tables — fact_factory_registration has a real date dimension (permit year); fact_catchment_place's local-area sources are point-in-time snapshots with none.

agg_economic_summary_yearly agg344 rows

Grain: geo_key × year. Factory-only (the only source with a real time dimension) — factory_count, investment sums, investment_per_worker, YoY growth.
Source data only spans permit years 2024–2025, so YoY growth is only computable for 2025 vs 2024. Most geo_keys show 0% YoY investment growth because the two registry snapshots report identical investment figures for most factories — confirmed real (one geo_key shows +1.3%, proving the calculation works when figures actually differ), not a bug.

feat_factory feat5,976 rows

Entity-grain feature store — one row per factory (vs. feat_geography_month's geography×time grain), ready for clustering/segmentation. Uses each factory's latest registration snapshot, not a sum/average across years.
Derived columnFormula
investment_per_workertotal_investment / total_workers
workforce_female_pctfemale_workers / total_workers × 100
No FK constraints — standalone, ML-readable without joining back into the warehouse, same intent as feat_geography_month.
