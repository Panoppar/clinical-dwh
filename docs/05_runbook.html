Prerequisites

  • Docker Engine with Compose v2 (Docker Desktop for local dev; plain docker + the docker-compose-plugin package for a Linux VM -- see Production (VM))
  • Outbound internet access to 6 live hosts (NSO, BMA, DIW, HDC, GitHub for the admin-boundary reference data, router.project-osrm.org) plus 2 that are currently blocked at the source, not this code (DDS, Overpass/OSM -- see Troubleshooting) — this pipeline has no offline mode
  • A local copy of the 4 file-based inputs under external-inputs/ (tambon crosswalk, DOPA population x2, BMA migrant worker permits) -- these are bind-mounted, not baked into the image, so updating any of them later needs no rebuild
  • Python 3 with pymysql on the host only if regenerating these docs directly (dumps information_schema to %TEMP%, see Day-2 Ops), or openpyxl if regenerating Excel\KPI_Tree_and_Dashboard_Design.xlsx

First-Time Deploy

  1. Clone and configure environment

    Copy-Item .env.example .env
Copy-Item seaweedfs_s3_config.json.example seaweedfs_s3_config.json
# Edit BOTH files: change every ChangeMe_* password.
# The access/secret key pair must match between the two files --
# .env is read by elt-runner; seaweedfs_s3_config.json is read
# directly by the SeaweedFS binary, not env-templated.

  2. Bring up infrastructure

    docker compose up -d warehouse-db landing-zone metabase
docker compose ps   # wait for warehouse-db and landing-zone to show "healthy"

    warehouse-db's healthcheck is mysqladmin ping; landing-zone's accepts any HTTP response (even 403) as healthy -- confirms the SeaweedFS S3 gateway is reachable, not that credentials are correct yet.

  3. Build and run the pipeline

    docker compose build elt-runner
docker compose run --rm elt-runner

    One-shot batch job, full Bronze -> Silver -> Gold refresh every time (idempotent). Ingests all 8 live-API sources (DIW's amphoe crawl takes ~70s; HDC's full 119-report crawl is the long pole, typically 10-20 min at its throttled rate -- watch for [ingest_api_hdc] (N/119)... advancing, this is normal, not a hang) and the 3 file-based sources. A source that's down (DDS, OSM -- both confirmed blocked at the source, not this code, see Troubleshooting) logs a warning and the run continues -- it will NOT abort the whole deploy.

Spot-check manually if any number looks off:

docker compose exec warehouse-db mysql --default-character-set=utf8mb4 -u root -p `
  -e "SELECT COUNT(*) FROM gold.fact_hdc_observation;"
Always pass --default-character-set=utf8mb4 explicitly on any manual mysql client invocation. Confirmed by direct testing: the MySQL server image's own bundled client defaults to latin1 and silently corrupts Thai string comparisons with no error raised.

Metabase Bootstrap

A brand-new Metabase container has no admin account and no database connections -- first boot shows a setup wizard. Two ways to complete it:

Option A -- UI wizard

Open http://localhost:3000, follow the prompts: create the admin account, then add a database connection (MySQL, host warehouse-db, port 3306, database gold, user metabase_ro, password = DWH_METABASE_RO_PASSWORD from .env).

Option B -- API (scriptable, used for this deploy)

Get the setup token, then POST the admin user. The embedded database object in /api/setup was unreliable on v0.50.19 in practice -- it silently succeeded without creating a connection. Add the database as a separate explicit call instead:

$token = (Invoke-RestMethod http://localhost:3000/api/session/properties).'setup-token'
Invoke-RestMethod -Method Post http://localhost:3000/api/setup -ContentType 'application/json' -Body (@{
  token = $token
  user = @{ first_name='Admin'; last_name='User'; email='you@example.com'; password='...'; site_name='clinical-dwh' }
  prefs = @{ site_name='clinical-dwh'; site_locale='en'; allow_tracking=$false }
} | ConvertTo-Json -Depth 5)

# Then log in and add the real database connection explicitly:
$session = (Invoke-RestMethod -Method Post http://localhost:3000/api/session -ContentType 'application/json' `
  -Body (@{ username='you@example.com'; password='...' } | ConvertTo-Json)).id
Invoke-RestMethod -Method Post http://localhost:3000/api/database -Headers @{'X-Metabase-Session'=$session} `
  -ContentType 'application/json' -Body (@{
    engine = 'mysql'; name = 'gold'
    details = @{ host='warehouse-db'; port=3306; dbname='gold'; user='metabase_ro'; password='...'; ssl=$false }
  } | ConvertTo-Json -Depth 5)

Verify sync completed: GET /api/database/{id}?include=tables, check every table shows "initial_sync_status":"complete".

A default "Sample Database" (Metabase's own H2 demo dataset, id=1 on a fresh instance) is added automatically during setup. Remove it for a clean workspace: DELETE /api/database/1 with the admin session header.

Production Deployment (VM)

Everything above works unchanged on a VM -- Docker Compose doesn't care whether it's running on a laptop or a server. The differences below are what actually matters once the warehouse is reachable over a network instead of just localhost, and left running unattended for weeks instead of a dev session.

Sizing (baseline, not a hard minimum)

  • 2 vCPU / 4GB RAM comfortably runs the 3 persistent services (MySQL, SeaweedFS, Metabase) idle; the elt-runner batch job is CPU-light (mostly waiting on throttled HTTP requests) so it doesn't need dedicated headroom, just enough to not starve the other 3 while it runs.
  • 20GB disk minimum. Current data footprint is small (38+ Bronze/Silver/Gold tables, largest at ~163K rows) -- the landing zone is the one that grows over time, though content-addressed dedup means a source that returns unchanged bytes on every re-run (the common case) adds nothing. Budget more if re-running frequently against sources that change often (HDC's own data updates faster than the others).

OS and Docker install

Docker Desktop is a dev-machine product -- a VM runs plain Docker Engine + the Compose v2 plugin instead (Ubuntu Server LTS is a reasonable default target):

# Ubuntu/Debian -- see docs.docker.com for other distros
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER   # log out/in once for this to take effect
docker compose version          # confirms the v2 plugin, not the old standalone docker-compose

Docker log limits -- already configured, verify it took effect

Every service in docker-compose.yml caps its own json-file log via a shared x-logging anchor (max-size: 3m, max-file: 2 -- 6MB worst case per service). Docker's own default has no cap at all, so this matters most on a VM where disk is finite and nobody's watching interactively. Confirm it's actually applied after bringing services up:

docker inspect cdw-warehouse-db --format '{{json .HostConfig.LogConfig}}'
# expect: {"Type":"json-file","Config":{"max-file":"2","max-size":"3m"}}
This caps container logs only. It does not cap the 3 data volumes (warehouse_db_data, metabase_data, landing_zone_data) -- those grow with real data, by design, and are what Day-2 backups below protect.

Persist across reboots

warehouse-db, landing-zone, and metabase already have restart: unless-stopped -- Docker itself restarts them after a host reboot, as long as the Docker daemon is enabled to start on boot (get.docker.com's installer does this automatically; confirm with systemctl is-enabled docker). elt-runner intentionally has no restart policy -- it's a one-shot batch job, not a daemon; scheduling re-runs is a cron concern, below.

Schedule periodic pipeline runs

There's no built-in scheduler -- a VM deployment that wants fresh data without someone running the command by hand needs a cron entry:

# /etc/cron.d/clinical-dwh-pipeline -- daily at 02:00 local time
0 2 * * * root cd /opt/clinical-dwh && docker compose run --rm elt-runner >> /var/log/clinical-dwh-pipeline.log 2>&1
Redirecting cron's own output to a plain log file sidesteps the container log cap above -- rotate that file too (logrotate, or just redirect to docker compose run --rm elt-runner 2>&1 | tail -n 1000 > /var/log/clinical-dwh-pipeline.log to keep only the latest run).

Network exposure

By default every port in docker-compose.yml binds to all interfaces (0.0.0.0) -- fine on a laptop behind a home router, not fine on a VM with a public IP.

  • Metabase (3000) is the only service end users need. If exposing it beyond the VM's own internal network, put a reverse proxy in front for TLS (Caddy or nginx with Let's Encrypt) rather than exposing Metabase's own HTTP port directly -- it has no TLS of its own.
  • warehouse-db (3306) and landing-zone (8333/8888) should not be internet-facing. Change their host-port bindings in docker-compose.yml from "${PORT}:3306" to "127.0.0.1:${PORT}:3306" (same pattern for the other two) so they're reachable from the VM itself and anything in the same Docker network, but not from outside -- nothing external needs direct DB or landing-zone access; Metabase already reaches warehouse-db over the internal cdw-net bridge network regardless.
  • If a cloud firewall/security-group is available at the VM level, use it as the primary control -- only open 22 (SSH) and whichever port fronts Metabase (443 if behind a reverse proxy, 3000 if not).

Secrets

  • Change every ChangeMe_* password in .env and seaweedfs_s3_config.json before this VM is reachable by anyone else -- the defaults in this repo are placeholders, not production credentials.
  • chmod 600 .env seaweedfs_s3_config.json -- both contain plaintext credentials; restrict to the deploying user.
  • Neither file belongs in version control -- confirm both are gitignored before pushing this VM's working copy anywhere.

Backups

The 3 named volumes are the entire state of the warehouse. A logical MySQL dump is more portable and consistent than a raw volume copy for the database specifically:

# Database -- logical dump, safe to take while the DB is running
docker compose exec warehouse-db mysqldump --default-character-set=utf8mb4 -u root -p --all-databases \
  > backup_$(date +%Y%m%d).sql

# Metabase + landing zone -- raw volume archives (stop the service first for a consistent snapshot,
# or accept a small risk of an in-flight write on a running one)
docker run --rm -v clinical-dwh_metabase_data:/data -v $(pwd):/backup alpine \
  tar czf /backup/metabase_$(date +%Y%m%d).tar.gz -C /data .
docker run --rm -v clinical-dwh_landing_zone_data:/data -v $(pwd):/backup alpine \
  tar czf /backup/landingzone_$(date +%Y%m%d).tar.gz -C /data .
The landing zone is re-derivable by re-running the pipeline against live sources (except DDS/OSM while those remain blocked, and the 4 file-based inputs, which only exist wherever external-inputs/ is kept outside the container) -- lower backup priority than the database itself, whose Gold layer took real compute (HDC's throttled crawl, OSRM's tiled routing) to rebuild from scratch.

Disk monitoring

docker system df            # image/container/volume disk usage at a glance
df -h /var/lib/docker        # or wherever Docker's data-root actually lives on this VM
docker system prune removes stopped containers, unused networks, and dangling images -- safe in general, but never run -a or --volumes without reading what it would remove first; --volumes can delete the named volumes this warehouse's entire state lives in if they're not currently attached to a running container.

Day-2 Operations

  • Re-run the pipeline any time: docker compose run --rm elt-runner. Idempotent -- the landing zone skips re-storing identical bytes, each layer's DDL drops/recreates its own tables.
  • Re-run just one source (faster than a full run while iterating): 
    docker compose run --rm elt-runner python -c "import ingest_api_nso, extract_load_api_nso; ingest_api_nso.run(); extract_load_api_nso.run()"
  • Regenerate these docs after any schema change -- dump the schema, then run the generator: 
    docker compose exec warehouse-db mysql --default-character-set=utf8mb4 -u root -p `
  -N -e "SELECT table_schema,table_name,column_name,column_type,is_nullable,column_comment,ordinal_position FROM information_schema.columns WHERE table_schema IN ('bronze','silver','gold') ORDER BY 1,2,7;" `
  > "$env:TEMP\schema_dump.tsv"
python docs\build_html_docs.py
  • Browse the landing zone at http://localhost:8888/buckets/landing-zone/ -- SeaweedFS's own Filer web UI (folders by source, file download/preview, upload/new-folder). Already running inside the landing-zone container via the server command; exposed to the host via LANDING_FILER_UI_HOST_PORT (default 8888) in docker-compose.yml. No separate client needed -- this is the "DBeaver for the landing zone."
  • Rebuild the elt-runner image after any Python/requirements change: docker compose build elt-runner

Troubleshooting

DDS returns 500 on every request. Check for "could not find driver (Connection: pgsql...)" in the response body -- that's DDS's own backend missing its PostgreSQL PHP driver, not fixable from this side. Nothing to do but wait and re-run ingest_api_dds.run() periodically.
NSO requests return an HTTP 418 block page. The WAF in front of NSO's API blocks the default requests/curl User-Agent. Confirm ingest_api_nso.py still sends User-Agent: Mozilla/5.0 kmch-phase3-nso/1.0 -- if NSO changes their WAF rules, the fix is a different UA string, not a code redesign.
OSM facility discovery returns HTTP 406 from every Overpass endpoint. Confirmed by direct testing (both from inside the container and from the host machine directly) that Overpass's public instance (overpass-api.de, including its lz4 mirror) is blocking this network origin -- unrelated to this code. ingest_api_osrm.py does not depend on this succeeding (it always computes the travel matrix to the fixed KMCH coordinate regardless), so this only affects dim_facility staying at 1 row (KMCH itself). Retry periodically; worth trying a different Overpass mirror if this persists.
landing-zone container is "unhealthy". Its healthcheck accepts any HTTP response as healthy (even 403) -- a real failure means the container can't be reached at all. Check docker compose logs landing-zone; a common cause is seaweedfs_s3_config.json missing (copy it from the .example if you skipped that step).
A full pipeline run seems to hang for ~15-20 minutes. That's the HDC crawl (119 reports x up to 5 years x 2 zones, throttled 0.6s between requests) -- not a hang. Watch the log for [ingest_api_hdc] (N/119)... lines advancing.

Full Reset

docker compose down -v   # removes containers AND volumes -- landed objects, warehouse data, Metabase state all gone
docker compose up -d warehouse-db landing-zone metabase
docker compose run --rm elt-runner
# then redo the Metabase Bootstrap section above -- a fresh volume means a fresh setup wizard
This deletes everything: every landed API response in SeaweedFS, every Bronze/Silver/Gold row, and the entire Metabase instance (admin account, saved questions, dashboards). Only run this when you genuinely want to start over.
